# 못 찾겠다 꾀꼬리

유아가 마우스나 손가락으로 입체 마을을 둘러보며 특정 주민을 찾는 키즈케이드 게임.

## 4차: 움직이는 거리와 연속 찾기 도전

- **기존 마을 찾기 유지**: 시간제한과 감점 없이 3D 주민·행동·소품을 비교
- **시민 동선 개선**: 빵을 배달하는 주민은 건물 앞 보행로의 별도 구역에서 이동, 공놀이·손 흔들기·독서·휴식은 동작에 맞게 표현. 보행 구역과 활동 구역을 분리하고 급격한 위치 변경 방지
- **도시 시각 개선**: 건물 임시 모델의 겹침 방지, 로딩 실패 시 사물과 맞지 않는 나무가 나타나는 현상 수정, 차량을 복수 도로 차로로 분산
- **조작 개선**: 카메라 회전 후에도 지면 기준 화면 드래그, 실제 3D 캐릭터 표면 우선 선택과 모바일 터치 판정 보정, 건물 뒤 주민 선택 방지
- **선택 도전 모드**: Critter Catchin'의 게임 규칙을 참고해 20초 제한, 오답 2초 차감, 방해 주민 10명부터 단계마다 3명 증가(최대 50명) + 별도의 정답 주민 1명, 10단계 이후 속도 상승, 정답 하나를 찾으면 다음 단계. 최고 기록 별도 저장
- 도전 모드는 일반 놀이와 점수·이어하기 기록을 공유하지 않음
- **원작 참고**: [100-Devs-1-Game/CritterCatchin](https://github.com/100-Devs-1-Game/CritterCatchin), MIT License (Copyright © 2025 100 Devs - 1 Game). 원작 에셋이나 Godot 스크립트를 복사하지 않고 게임 메커니즘을 별도 구현

## 3차: 생활 장면과 관찰 문제

- 작은 마을 18명/1명 찾기, 중간 마을 45명/3명 찾기, 대도시 84명/5명 찾기
- 빵집(빵 고르기·배달·먹기), 공원(독서·공놀이·벤치 휴식), 정류장(기다리기·인사·지도 보기)의 생활 장면 9종
- 그림 비교·행동 비교·소품 비교의 난이도를 도시 크기와 별도로 선택. 중간·어려운 단계에서는 모든 정답에 의도적인 유사 인물을 배치
- 고유한 모델·활동·소품 조합. 배경 인물은 18~32초부터 활동을 순환하며 정답과 유사 인물은 문제 중 행동 유지
- Poly Pizza 도시 건물·상점·버스 정류장·자전거·우체통·화분, Kenney 가로등·인물·차량·음식 등 보유 에셋 활용. 건물은 가로·세로 2.6 이내로 제한해 보행로 확보
- 실제 대상의 3D 미리보기 회전, 카메라 90도 회전, 건물 너머 보기, 건물 터치 시 6초간 낮추기, 가려진 주민 선택 방지
- 얼굴을 비교할 수 있는 시작 배율, 모바일 가로형 찾기 카드, 클릭·터치, 지도 이동, 확대, 음성 단서, 세 단계 힌트
- 정답의 짧은 반응과 발밑 표시, 찾은 친구 도장, 비교 요소를 알려 주는 오답 안내, 완주, 자동 저장·새로운 하루
- 캐릭터·포즈·핵심 소품 로딩 확인 후 출제. 불러오지 못한 조합은 정답에서 제외. 생성 규칙이 다른 이전 버전의 저장은 이어받지 않음
- 일반 마을 찾기에서는 잘못 선택해도 감점·시간제한 없음. 정답 인물은 게임 중 사라지거나 화면 밖으로 순간 이동하지 않음

### 2026-10-30: early delivery and honest browser motion checks

Delivery residents begin their first errand after 0.8–1.8 simulated seconds,
before browsing/resting residents (3–12 seconds) reserve shared corridors.
The same single RNG draw is consumed per resident, preserving seeded looks and
saved target order. Path reservations, collision clearance and normal activity
routines remain in force. A 100-seed regression checks visible early departure;
existing long town simulations continue to check spacing and cross-block travel.

The actual Chrome audit now follows stable delivery IDs until natural departure,
then compares rendered 3D coordinates with the simulation. It no longer assumes
one current activity/slot must move within a fixed 1.7-second wall-clock window.
Frozen rendering, mismatched identities and simulation-only movement still fail.

## 2026-11-08 — 빵집에서 다른 동네까지 이어지는 실제 심부름

- **실제 생활 상태 전이:** 자유롭게 돌아다니는 배경 주민이 빵집·시장에 도착해 빵을 고른 뒤 하나의 빵(`propVariant`)을 구입합니다. 그 빵을 손에 들고 연결된 인도를 따라 **다른 블록의 공원/주택가**로 이동해 각각 먹거나 전달합니다.
- 보행 중 작은 쇼핑백을 보여 주고, 공원에 도착하면 먹는 동작으로, 집에 도착하면 배달하는 동작으로 표현합니다. 화면 동작을 위한 `getVisualActivity`는 정답을 구분하는 `signature`와 분리해 문제의 외형 유일성을 보존합니다.
- 통로를 막거나 경로를 순간 이동하지 않도록 기존 경로 예약과 도착 후 활동 시간을 그대로 사용합니다. 목적지가 혼잡하면 가게에서 대기하거나 다른 공원/집을 선택합니다.
- 타깃 주민·의도적인 유사 인물, 시간제한 챌린지에는 생활 심부름을 적용하지 않습니다. 기존 시드·정답 순서·게임 기록·저장 버전(3)은 그대로 유지합니다.
- 완료된 생활 경로는 개인정보 없이 최근 12개만 `town.commerce.recent`에 저장하며, 새 게임 시작 시 초기화합니다. 수업 화면에 개발용 상태를 표시하지 않습니다.
- 실제 버스 탑승/하차와 장거리 교통 연결은 아직 미구현입니다. 이 심부름은 다른 주민에게 직접 건네는 애니메이션까지 구현한 것은 아닙니다.

## 2026-11-09 — 차와 보행자가 같은 신호를 보는 실제 교차로

- 이전에는 차 1~3대가 `game.js`의 독립 시간값으로 화면만 좌우 이동해 버스·보행자와 실제 상호작용하지 못했습니다. 이제 일반 마을의 `traffic.mjs`가 **공통 도로·횡단보도·교차로 그래프**에서 차량의 이동을 담당합니다. Three.js의 기존 세단/택시/밴 GLB는 그 시뮬레이션 좌표에 맞춰 렌더링됩니다.
- 교차로는 수평 녹색 → 전적색 → 수직 녹색 → 전적색의 순환 신호를 가지고, 3D 신호등의 두 표시등 색도 동일하게 바뀝니다. 주행 중 신호가 바뀌더라도 교차로 한가운데 멈추지 않고 빠져나옵니다.
- 자동차는 **실제 횡단보도의 양쪽 연결을 모두 확인**한 뒤 건너는 주민에게 양보합니다. 자동차가 이미 횡단보도를 통과 중이라면 새로 진입하려는 주민은 짧게 기다립니다. 보도와 차도를 구분하기 위해 자동차는 폭 1.35의 도로 중심선을 사용합니다.
- 버스도 같은 신호를 따르며, 일반 차량이 있는 수평 도로를 달려야 할 때는 먼저 지나가게 한 뒤 해당 도로를 버스가 이동하는 동안 예약합니다. 목적지의 지정된 정류장 자리가 잠시 차 있으면 **정류장 안에서 대기**하며, 직선이 아닌 다른 빈 자리로 무리하게 하차시키지 않습니다.
- 교차로의 3D 신호등은 주민을 선택하는 Raycaster에 들어가지 않습니다. 정답·유사 인물·빵집 심부름·저장 버전 3·모바일 조작·도전 모드의 기존 규칙은 변경하지 않았습니다. 도전 모드에는 교통 제어 대신 기존 장식 차량만 표시합니다.
- **직접 V8 시뮬레이션:** 3개 도시×3개 난이도×4개 시드의 36개 마을을 각각 600초 실행. 전부 실제 승하차 및 0.85 이상의 보행자·자동차 거리 확인, 버스·자동차 중심 거리 1.7 이상, 보행자가 5초 이상 막히는 문제 없음. 이전 버스 PR #749와 900개 마을의 초기 정답·외형·위치 동일. GitHub Actions Node/Chrome 결과는 별도로 기록합니다.
- 한계: 수평 도로에서 버스가 주행하는 동안 다른 일반 차량을 잠시 도로 밖에서 대기시키는 단순 안전 예약을 사용합니다. 물리적 다차선·우회전, 개별 신호 최적화, 실제 모바일 FPS, 인간이 직접 보는 스크린샷의 조형 검수는 다음 과제입니다.

## 2026-11-10 — 버스 차체·하차 플랫폼·태블릿 렌더링

- 버스가 주민과 겹치지 않도록 버스 **전체 길이·폭**에 보행자 반경을 더해 횡단·보행을 판정합니다. 차체를 중심점 하나로만 계산하지 않습니다.
- 버스 승객은 일반 주민의 활동 칸이 아닌 **정류장 안쪽 별도 플랫폼**에서 내려, 노란 짧은 연결 통로를 따라 기존 일방통행 인도로 합류합니다. 나간 뒤에는 같은 구역의 비어 있는 자리나 다음 목적지로 실제 걸어갑니다.
- 교통 버스·자동차 GLB와 예비 모델은 차체의 긴 축을 실제 도로의 진행 방향에 맞춥니다.
- 터치/태블릿에서 대도시 메인 WebGL DPR은 최대 1, 다른 도시 최대 1.12, 미리보기 최대 1.0으로 제한하고 미리보기는 최대 초당 24회 렌더링합니다. 데스크톱은 기존 해상도 상한 1.55를 유지하며 저장 기록·정답·조작법은 변경하지 않습니다.
- 검증: 3도시×3난이도×4시드, 각 300초 시뮬레이션에서 실제 버스/보행자 차체 겹침 0, 모든 시드 승하차, 일반 보행 최대 대기 2.6초. 초기 퍼즐 900개 조합 정답/외형/좌표 동일. 실제 Chrome GLB 크기 검사는 수행했으나 **iPad 실기기 FPS·수동 시각 판독은 미수행**.
- 한계: 소형 마을의 단일 승객 버스는 플랫폼 점유에 따른 대기가 최대 약 110초까지 생길 수 있어 후속 개선 필요. 개선 내용은 최신 main 기준 **PR #757**에 이관되었으며 기존 PR #756은 병합 없이 종료했습니다. **#757도 아직 병합·배포 전입니다.**
