# 《내 말 좀 들어》 v5 — 돌아오면 길이 달라지는 규칙 미로

> 상태: **설계 전용**. 아래 시제품 2개는 별도 JSON이며 본편 60단계에는 아직 삽입하지 않았다. 플레이 기록이나 라이브 게임 코드는 건드리지 않았다.
>
> 실제 확인한 기반: levels.js의 60개 단계, rules.js, movement.js, interactions.js, turn.js, validator.js, ui/fog.js, MAZE_REWORK.md.

## 1. 왜 57개 지형만으로는 충분하지 않은가

v4에서 벽 배치는 15종에서 57종으로 늘었지만, 현재 자동 지도 검사는 벽 위치를 따라 정적으로 탐색하는 방식이다. 규칙 변화, 물체 밀기, 여러 YOU의 동작, 변환을 고려하지 않은 갈림길 수는 실제 난이도의 근거가 되지 못한다.

v5의 핵심은 방 수가 아닌 인과관계다.

1. 처음 만난 문이 왜 닫혔는지 발견한다.
2. 다른 방에 가야만 바꿀 수 있는 규칙이 있다는 사실을 추론한다.
3. 그 규칙을 조작한다.
4. 이미 지나온 곳으로 돌아와 변화된 길을 사용한다.
5. 후반에는 두 번째 작업실, 새 조종 객체, 변환된 물체까지 연쇄로 활용한다.

빈 막다른 골목과 불필요한 왕복은 점수를 주지 않는다. **규칙 변경이 유효한 지형 선택을 바꿀 때**만 의미 있는 미로가 된다.

## 2. 60단계 난이도 곡선

| 범위 | 기존 챕터 | 새 설계 목표 |
|---|---|---|
| 1~6 | 규칙의 문 | 1~3단계 조작 학습, 4~6단계 첫 왕복과 간단한 규칙 조작 |
| 7~16 | 법칙을 깨라 | 관문과 작업실을 분리하고 규칙 해제 후 복귀 |
| 17~26 | 나는 누구? | 여러 YOU가 서로 다른 방에 접근하고 역할 분담 |
| 27~36 | 세상을 바꿔라 | 변환 전후에 같은 장소의 기능이 달라짐 |
| 37~46 | 두 법칙 | 공간적으로 떨어진 두 법칙을 올바른 순서로 조작 |
| 47~55 | 규칙 연구소 | 자동 MOVE, WEAK과 위험 개체의 이동을 이용한 공간 퍼즐 |
| 56~60 | 금지된 실험 | 2회 이상 작업실-관문 복귀, 역할 전환과 변환을 결합 |

각 단계별 현재 제목과 추천 공간 패턴, 규칙 변경 목표, 복귀 목표를 **design-prototypes/stage-blueprints-v5.json**에 60개 모두 기록했다. 그 파일의 수치는 목표치이지 이미 구현된 난이도나 솔버의 결과가 아니다. 자동 이동이나 다중 YOU 중심 단계에는 단어 변경 없이도 중요한 조종 전환이 성립할 수 있다.

## 3. 검증 가능한 시제품 A — 돌아온 길

파일: design-prototypes/return-route.json

    ·ttt··I·ttt·
    ······I·····
    ·H····W···F·
    II·IIII·····
    ······I·····
    IIII·II·····
    ······I·····
    ··ttt·I·····
    ······I·ttt·
    ······I·····

H=아이, F=목표, W=벽, I=얼음, t=글자.

- 처음에는 가운데 W 관문이 WALL = STOP 때문에 통과되지 않는다.
- 아래 작업실에서 WALL = STOP 문장의 마지막 글자를 밀어 규칙을 끊는다.
- 얼음은 별도의 ICE = STOP 규칙으로 막혀 있으므로, 규칙을 끊은 자리에서 오른쪽으로 바로 빠져나갈 수 없다.
- 처음 관찰한 W 관문으로 되돌아와 지나간다.
- 실제 턴 엔진을 사용한 시제품 검증: **23수, 필수 규칙 해제 1회, 클리어 확인.** 이는 기록한 하나의 해법이며 최단해라는 증거는 아니다.

## 4. 검증 가능한 시제품 B — 두 번 열리는 문

파일: design-prototypes/dual-gate.json

    ·ttt·I··ttt·
    ·····I···I··
    ·H···W···DF·
    ·····I···I··
    ·····I···I··
    ·····I···I··
    ·····I·t·I·t
    ·ttt·I·t·I·t
    ·····I·t·I·t
    ·····I···I··

- 왼쪽 아래 작업실에서 WALL = STOP을 끊으면 첫 번째 관문 W가 열린다.
- 가운데 작업실로 이동해 DOOR = STOP을 끊으면 두 번째 관문 D가 열린다.
- 두 관문을 열더라도 ICE = STOP 차단막이 남아 불필요한 지름길을 제한한다.
- 실제 턴 엔진 검증: **33수, 서로 다른 규칙 해제 2회, 클리어 확인.** 최단해 보장은 아니다.

주의: ICE = STOP은 현 엔진의 일반적인 **가변 규칙**이다. 시제품에서는 최종 방 너머에 이 문장을 두어 해법 중 유지하도록 했지만, 이 타입 자체를 불변 지형이라고 오해해서는 안 된다.

## 5. 실전 맵의 공간 문법

다음 유형을 섞고 동일 유형을 연속 반복하지 않는다.

- **관문–작업실–귀환**: 처음 막힌 관문을 기억하고 다른 방에서 글자를 조작해 돌아오기.
- **두 작업실 연쇄**: 첫 규칙 해제가 두 번째 방의 입장 조건이 됨.
- **다중 YOU 원격 해결**: 아이와 돌 등이 각자의 위치에서 서로 다른 사물을 밀어 주기.
- **변환 후 귀환**: 돌이 물이 된 뒤 기존 좁은 길이 새 통로로 달라짐.
- **위험 방의 되돌릴 수 있는 선택**: 물·불·얼음·열쇠 조합을 원인과 결과가 읽히게 구성.
- **MOVE 타이밍**: 이동하는 위험이나 목표에 맞춰 규칙을 변경하고 길을 선택.

막다른 길은 단서, 목표 관찰, 나중에 쓸 관문 중 하나의 의미가 있어야 한다. 시작점과 목표를 계속 같은 위치에 놓지 않는다. 12×10 이상의 보드는 작은 모바일 화면에서 가독성이 떨어질 수 있으므로 먼저 기존 크기에서 검증한다.

## 6. 고정 지형과 규칙 대상 분리 — 권장 엔진 변경

현재 모든 벽/얼음/문은 단어의 속성 규칙이 바뀌면 전역적으로 성질이 바뀐다. 미로 외곽과 좁은 문 한 칸을 모두 WALL로 만들면 문 하나를 열려다가 테두리 전체가 통과 가능해질 수 있다.

선택적 level.terrain 배열을 제안한다.
- terrain의 SOLID 타일은 어떤 문장도 바꿀 수 없는 기초 지형이다.
- objects의 WALL, DOOR, ICE는 계속 규칙에 반응하는 대상이다.
- Movement, Renderer, Validator, Editor, History가 같은 terrain 모델을 사용한다.
- 새 스키마가 없는 기존 60단계는 **100% 동일하게** 동작한다.
- 현 시제품의 ICE = STOP 고정벽은 이 기능이 도입되면 고정 지형으로 대체하는 것을 우선 검토한다.

## 7. 난이도를 수치로 검증하는 방법

현재 Validator.analyzeTopology는 벽에만 반응하므로 아래 **동적 검사**가 필요하다.

1. 게임에 들어가는 상태와 동일하게 레벨을 초기화한다.
2. 방향키 입력은 오직 E.Turn.step을 호출해 시뮬레이션한다.
3. 물체 ID, 타입, 단어, 좌표, 방향, 제거 여부가 같은 상태를 중복 방문하지 않도록 한다.
4. 최소 한 개의 실제 엔진 입력 시퀀스인 **골든 해법**을 각 단계에 저장한다.
5. 규칙 변경이 필수인 단계에는 문장을 움직이지 않고는 목표를 달성할 수 없는지 탐색한다.
6. 다중 YOU와 MOVE 문제는 단어 변경 횟수 대신 조종권 변동과 위험 타이밍의 필수성을 별도로 본다.
7. 자동 탐색이 예산을 소진하면 **search-limit**로 기록하고 절대 풀 수 있다거나 풀 수 없다고 확정하지 않는다.
8. 골든 해법, 짧은 지름길, 사물 교착, 목표 소실, 무조종 상태를 각각 검출한다.

체크할 핵심 지표는 **실제 규칙 개입 수, 이전 지역 재방문 수, 관문 상태 변화, 정상 해법 수, 부당한 우회 해법 여부**다. 복잡한 갈림길 개수는 보조 지표일 뿐이다.

## 8. 화면·힌트·접근성

- 규칙 해제 시 해당 문이 열렸다는 짧은 시각 효과, 현재 활성 규칙 강조.
- 단어의 위치와 의미를 색뿐 아니라 글자·표시로 구별한다.
- 탐험 안개는 현행처럼 켜고 끌 수 있으며, 처음 학습하는 단계에는 강요하지 않는다.
- 힌트 1은 관찰 질문, 2는 관련 규칙, 3은 구체적 조작. 길게 읽는 설명보다 짧은 안내.
- 타이머, 하트 소모, 반복 실패 벌점을 추가하지 않는다. 이동 실수는 되돌리기/재실행으로 복원할 수 있어야 한다.
- 모바일에서 조작 버튼이 규칙 단어를 가리지 않아야 한다. 한 칸 이동과 길게 누르기를 확실히 구분한다.

## 9. 진행 기록 호환

현재 라이브 본편의 progress_v3 저장은 단계별 cleared와 best를 보관한다. v5에서 지형이나 풀이가 달라지면 과거 최적 이동 수와 새 이동 수를 동일 순위로 비교하면 안 된다.

- 기존 완주·잠금 해제 상태는 보존.
- 최고 기록은 퍼즐 설계 버전별로 분리. 이전 기록은 기록 보관함에서 표시.
- 마이그레이션은 반복 실행해도 안전하고, 저장이 안 되어도 플레이 자체는 가능해야 한다.
- 우선 7~16단계의 소수 파일럿만 바꾸고 검수 후 확대. 초반 튜토리얼은 보존.

## 10. 개발 순서와 승인 기준

| 단계 | 구현 작업 | 승인 조건 |
|---|---|---|
| 1 | 실제 엔진 골든 해법 러너, 상태 해시, 관문 검사 | 시제품 2종과 기존 회귀 통과 |
| 2 | 선택적 terrain 충돌 및 에디터 | 옛 60단계에 영향 없음 |
| 3 | 7~16단계 중 4개 파일럿 | 해법, 의미 있는 복귀, 모바일 조작 통과 |
| 4 | 17~36단계 다중 YOU·변환 | 원격 조종과 변환의 필수성 입증 |
| 5 | 37~60단계 다중 규칙·MOVE | 모든 변경 단계 골든 경로 증명 |
| 6 | 단계별 버전 기록·안개·힌트 조율 | 시각 검수, 사용성 검수 후 병합 |

**라이브 교체 품질 게이트:** 단계 의도, 엔진 재생 정답, 핵심 규칙의 필수성, 교착 및 지름길 검사, 화면 검수 5가지가 준비되어야 한다.
